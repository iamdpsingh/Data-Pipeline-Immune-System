# Incident Response & Operations Runbook

This guide establishes standard operating procedures (SOPs) for responding to alerts generated by the **Data Pipeline Immune System**, managing operator approvals for high-risk actions, clearing hard blocks, and inspecting the BigQuery audit trail.

---

## 1. Incident Severity Matrix & SLAs

Every detected incident is classified into a standardized severity tier that determines automated remediation eligibility, alerting channels, and target Mean Time to Resolution (MTTR).

| Severity | Definition & Examples | Notification Channel | Auto-Remediable? | Target MTTR |
|---|---|---|---|---|
| **P0** | **Critical Safety / Privacy Violation**<br>• PII column detected in source feed<br>• Never-allow boundary action attempted | PagerDuty + `#data-incidents-p0` | **NO** (Hard Blocked) | < 5 mins |
| **P1** | **Pipeline Blocker / Severe Data Defect**<br>• Row drop > 40% below baseline<br>• Breaking schema drift (dropped column)<br>• Repeated pipeline crash (3+ in 24h) | Slack `#data-ops` + On-call | **Conditional** (Requires sign-off for breaking changes) | < 15 mins |
| **P2** | **Recoverable Degradation**<br>• Transient Airflow task crash (OOM, timeout)<br>• Upstream API 504 gateway timeout<br>• Missing historical partition | Slack `#data-alerts` | **YES** (Auto-remediated) | < 30 mins |
| **P3** | **Minor / Additive Change**<br>• Non-breaking additive schema expansion<br>• Minor null variance within tolerance | Dashboard Telemetry | **YES** (Auto-remediated) | < 2 hours |

## 2. Operator Approval Workflow for High-Risk Actions

When the [RiskAgent](file:///Volumes/Work/daemons-lab/d.automation/Data%20Pipeline%20Immune%20System/agents/risk_agent.py) assesses an incident as **HIGH RISK** (e.g. `SCHEMA_BREAKING_CHANGE` requiring `QUARANTINE_BAD_RECORDS`), automated execution is paused. The incident enters `ACTION_SELECTED` state awaiting human engineer authorization.

### Review Procedure:
1. **Navigate to the Dashboard**: Open `dashboard/index.html` or inspect pending incidents via API:
   ```bash
   curl -s http://localhost:8080/health
   ```
2. **Review the Incident Context in BigQuery**:
   ```sql
   SELECT
     i.incident_id,
     i.pipeline_id,
     i.incident_type,
     i.severity,
     i.root_cause,
     i.confidence,
     a.action_type,
     a.details
   FROM `data-pipeline-immune-system.dpis_dev.incidents` i
   JOIN `data-pipeline-immune-system.dpis_dev.audit_log` a ON i.incident_id = a.incident_id
   WHERE i.status = 'ACTION_SELECTED'
   ORDER BY i.detected_at DESC
   LIMIT 1;
   ```
3. **Approve via API Endpoint**:
   ```bash
   curl -X POST http://localhost:8080/api/v1/incidents/approve \
     -H "Content-Type: application/json" \
     -d '{
       "incident_id": "inc-77f98d",
       "approved_by": "oncall_engineer@company.com",
       "approval_id": "appr-20261023-01",
       "pipeline_id": "orders"
     }'
   ```
4. Once authorized, the Remediation Agent applies the approved handler, the Verification Agent re-checks post-repair metrics, and the incident transitions to `RESOLVED`.

## 3. Clearing Hard Blocks (P0 Violations)

When a P0 violation occurs (such as an incoming column matching PII patterns), the pipeline is **BLOCKED** and the controller refuses automated remediation.

### Investigation & Clearing Steps:
1. **Identify the Offending Source Record / Column**:
   ```sql
   SELECT details, timestamp
   FROM `data-pipeline-immune-system.dpis_dev.audit_log`
   WHERE action_type = 'INCIDENT_BLOCKED'
   ORDER BY timestamp DESC
   LIMIT 1;
   ```
2. **Upstream Mitigation**:
   - Contact the upstream provider to drop or mask the sensitive attribute at source.
   - If the attribute is legitimate and approved by data governance, add the schema exception to `rules/detection_rules.yaml`.
3. **Clear the Pipeline Block**:
   ```bash
   # Unblock the pipeline registry entry
   python3 -c "
   from src.controller.controller import ImmuneSystemController
   from src.controller.states import IncidentState
   # Update incident status in BigQuery to ESCALATED or RESOLVED
   print('Clear incident block acknowledged by operator.')
   "
   ```

## 4. Querying the Incident Audit Trail

All actions and state transitions are queryable in BigQuery:

### Recent Incidents Summary:
```sql
SELECT
  incident_id,
  pipeline_id,
  incident_type,
  severity,
  status,
  root_cause,
  confidence,
  detected_at,
  resolved_at,
  TIMESTAMP_DIFF(resolved_at, detected_at, MINUTE) AS mttr_minutes
FROM `data-pipeline-immune-system.dpis_dev.incidents`
ORDER BY detected_at DESC
LIMIT 10;
```

### Full Agent Decision Sequence:
```sql
SELECT
  event_id,
  agent_name,
  action_type,
  status,
  details,
  timestamp
FROM `data-pipeline-immune-system.dpis_dev.audit_log`
WHERE incident_id = 'inc-77f98d'
ORDER BY timestamp ASC;
```
